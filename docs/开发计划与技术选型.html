02开发方法论（不变）

2.1 骨架先行（Walking Skeleton）

先搭一个「能从头到尾走通、但业务为空」的最小骨架：登录页能打开、能调通一个后端接口、能读写数据库、能跑 CI。骨架跑通后，业务功能就像往骨架里「填肉」，风险极低。

为什么先搭骨架？ 骨架阶段会暴露所有基础设施级问题（环境、构建、认证、数据库连接、部署链路、跨端通信）。这些问题若拖到业务开发中期才遇到，返工成本极高。骨架是一次性投入，长期受益。

放弃「先做完所有数据库 → 再做所有接口 → 再做所有页面」的横向分层，改用垂直切片：每个功能模块一次性穿透所有层。

4.2 架构风格：模块化单体优先

不直接上微服务。采用「模块化单体（Modular Monolith）」：一个二进制应用，但按业务域严格分包，模块间只通过明确的 Service 接口调用，禁止跨模块直接访表。未来任一模块成为瓶颈，可整块抽出为独立服务。

单个模块的内部分层（以 auth 为例）

  • handler.go —— HTTP 层：参数绑定、调用 service、返回统一响应
  • service.go —— 业务逻辑层：编排、事务、调用其他模块的 Service 接口
  • repository.go —— 数据访问层：GORM 查询，只操作本模块的表
  • dto.go —— 请求/响应结构体 + 校验标签
  • model.go —— 数据库模型（GORM struct）
  • router.go —— 该模块的路由注册（挂载到全局路由组）
依赖倒置Service 层依赖接口而非具体实现，Repository 实现接口。这样单元测试可注入 mock，模块拆分时只需替换实现。

05前端技术栈（Vue 全家桶 + uni-app）

核心策略：全前端统一 Vue 生态。后台、讲师端、移动端、PC 端、桌面端都是一套 Vue 语言与组件心智，跨端复用最大化。

端技术栈开发顺序说明
管理后台 WebVue3 + Vite + Element Plus + Pinia + Vue Router第 1 批平台运营中枢，最先做，用于录入数据
讲师操作 WebVue3 + Vite + Element Plus（共享组件包）第 1 批与后台共享 @yanmai/ui 组件
小程序 / H5 / APPuni-app（Vue3 + Vite）+ uni-ui第 1 批一套代码出微信小程序 + H5；后期直接补 APP
用户 PC 端Nuxt 3（Vue SSR）第 2 批课程页 SSR 利于 SEO
桌面客户端Tauri 2 + Vue3第 3 批复用 Web 组件，离线学习
为什么后台也改成 Vue？ 你选了 uni-app，而 uni-app 是 Vue 语法。如果后台用 React，团队要同时维护两套语言、两套组件体系、两套状态管理，心智负担与人力成本翻倍。统一到 Vue + Element Plus，所有端共享 @yanmai/ui 与工具函数，是最省力的选择。

共享包（前端复用的关键）

UI@yanmai/ui

按《UI 设计规范》实现的设计系统组件库（Vue3），各端适配。

SDK@yanmai/api-client

由后端 OpenAPI 自动生成的类型安全 TS SDK，接口变更自动同步。

共用@yanmai/shared

共享类型、常量、工具函数、校验规则、业务逻辑。

Phase 1 — 工程骨架（Walking Skeleton）下一个确认点 ⭐

目标：交付一个「能跑起来、能登录、能调通接口」的空壳项目。技术栈：Go+Gin / Vue3+Element Plus / uni-app / 云 PostgreSQL。
